Sandbox as WebAssembly
======================

Sandbox can be built as WebAssembly, using Emscripten_. The result runs under
node, or in a web browser, where the U-Boot console appears in a terminal on a
web page. Nothing is installed and nothing runs on a server: the browser runs
U-Boot itself, with its emulated devices, commands and unit tests.

This is experimental. See `Limitations`_ below.

Building
--------

Install the Emscripten SDK and activate it, so that emcc is in your path::

    git clone https://github.com/emscripten-core/emsdk.git
    cd emsdk
    ./emsdk install latest
    ./emsdk activate latest
    source ./emsdk_env.sh

Then build with emcc as the compiler, using the LLVM tools which come with
the SDK::

    B=/path/to/emsdk/upstream/bin
    make O=/tmp/b/sandbox_wasm CC=emcc AR=emar NM=$B/llvm-nm LD=$B/wasm-ld \
        OBJCOPY=$B/llvm-objcopy OBJDUMP=$B/llvm-objdump sandbox_wasm_defconfig
    make O=/tmp/b/sandbox_wasm CC=emcc AR=emar NM=$B/llvm-nm LD=$B/wasm-ld \
        OBJCOPY=$B/llvm-objcopy OBJDUMP=$B/llvm-objdump -j$(nproc)

CONFIG_SANDBOX_WASM is enabled automatically when the compiler targets
WebAssembly.

Running under node
------------------

The u-boot file is a JavaScript loader for u-boot.wasm, so run it with node.
It can see the host's files::

    cd /tmp/b/sandbox_wasm
    node u-boot -d arch/sandbox/dts/sandbox.dtb

Use -T instead of -d to run the unit tests with the test devicetree::

    node u-boot -T -c "ut hush"

Running in a browser
--------------------

The u-boot-web.js and u-boot-web.wasm files hold the browser build, with the
devicetree included. The arch/sandbox/wasm/u-boot.html page loads them and
connects the console to an xterm.js_ terminal. A browser does not load
WebAssembly from a file:// URL, so serve the files over HTTP::

    cd /tmp/b/sandbox_wasm
    cp /path/to/u-boot/arch/sandbox/wasm/u-boot.html .
    python3 -m http.server 8000

Then open http://localhost:8000/u-boot.html

How it works
------------

Sandbox already runs as a normal program on top of the C library, so most of
it compiles unchanged. These are the parts which differ:

Linker lists
    Drivers, commands, unit tests and the like are collected in linker lists.
    Each entry is in its own section and the linker script sorts the sections
    by name, so that each list forms an array. wasm-ld has no linker scripts
    and lays out data in the order of its input. So the build links U-Boot
    into a single relocatable object, then scripts/wasm_sort_lists.py moves
    the linker-list segments to the end of that object's data section, in
    sorted order, updating the symbol table and relocations to match. The
    final link then keeps that order.

Console
    A web page cannot block waiting for input. The sandbox serial driver polls
    for input, sleeping briefly each time with os_usleep(). In this build that
    calls emscripten_sleep(), which uses Asyncify to return to the browser's
    event loop. The page supplies keypresses through Emscripten's stdin
    callback, which reports that there is no data yet rather than blocking.

Symbol clashes
    U-Boot has its own functions called putc(), fputc(), fputs(), fflush(),
    getopt() and sbrk(). On other hosts U-Boot's version quietly replaces the
    C library's one. With WebAssembly a call to a function with a different
    signature traps, and the C library's allocator needs its own sbrk(), so
    these are renamed with a ub\_ prefix.

Types
    This is a 32-bit target where size_t is unsigned long and file offsets
    are 64 bits.

System headers
    Emscripten has no Linux UAPI headers, so arch/sandbox/wasm/include holds
    stand-ins for the few which the files built with system headers need.

Embedded files
    Fonts, images and devicetrees are embedded using assembly files which
    are generated by the build. The WebAssembly assembler has a different
    syntax for section flags and needs the type and size of each symbol.

Limitations
-----------

- Loaded code cannot be executed, so EFI applications cannot be run and
  CONFIG_EFI_LOADER is disabled. SPL, TPL and VPL builds are not supported,
  since each phase starts the next with execve()
- The 'reset' command cannot restart U-Boot. Reload the page instead
- There is no display, since SDL is not connected up yet
- Host networking (raw sockets and tap devices) is not available
- uthread, the TKey driver, LUKS, exFAT and the exception command are
  disabled
- Error numbers from the C library differ from those which U-Boot uses, so
  an error from a host file operation can be reported as the wrong error
- Some unit tests assume a 64-bit host or files which the Python test suite
  creates
