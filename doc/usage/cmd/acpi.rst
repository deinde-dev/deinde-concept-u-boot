acpi command
============

Synopsis
--------

::

    acpi list [-c]
    acpi items [-d]
    acpi dump <name>
    acpi set [<address>]

Description
-----------

The *acpi* command is used to dump the ACPI tables generated by U-Boot for
passing to the operating systems. It allows manually setting the address to take
a look at existing ACPI tables.

ACPI tables can be generated by various output functions and even devices can
output material to include in the Differentiated System Description Table (DSDT)
and SSDT tables (Secondary System Description Table). U-Boot keeps track of
which device or table-writer produced each piece of the ACPI tables.

The ACPI tables are stored contiguously in memory.


acpi list
~~~~~~~~~

List the ACPI tables that have been generated. Each table has a 4-character
table name (e.g. SSDT, FACS) and has a format defined by the
`ACPI specification`_.

The `-c` flag tells U-Boot to verify the checksums, showing 'OK' or 'bad' next
to each table. The RSDP has two checksums, one over its first 20 bytes and one
over the whole table, so it shows two verdicts.

U-Boot does not currently support decoding the tables. Unlike devicetree, ACPI
tables have no regular schema and also some include bytecode, so decoding the
tables requires a lot of code.

The table shows the following information:

Name
    Table name, e.g. `MCFG`

Base
    Base address of table in memory

Size
    Size of table in bytes

Detail
    More information depending on the table type. The Firmware ACPI Control
    Structure (FACS) has no header fields, so nothing is shown for it, not
    even a checksum

    Revision
        Table revision number (two decimal digits)

    OEM ID
        ID for the Original Equipment Manufacturer. Typically this is "U-BOOT".

    OEM Table ID
        Table ID for the Original Equipment Manufacturer. Typically this is
        "U-BOOTBL" (U-Boot bootloader)

    OEM Revision
        Revision string for the Original Equipment Manufacturer. Typically this
        is the U-Boot release number, e.g. 20220101 (meaning v2022.01 since the
        final 01 is not used). For DSDT, this is set by the source code in
        the parameters of DefinitionBlock().

    ACPI compiler-vendor ID
        This is normally `INTL` for Intel

    ACPI compiler revision
        This is the compiler revision. It is set to the version string for the
        DSDT table but other tables just use the value 0 or 1, since U-Boot does
        not actually use the compiler in these cases. It generates the code
        itself.

acpi items
~~~~~~~~~~

List the ACPI data that was generated, broken down by item. An item is either
an ACPI table generated by a writer function, or the part of a table that was
generated by a particular device.

The `-d` flag also shows a binary dump of the table.

U-Boot keeps this breakdown only when it generates the tables itself, so the
command reports that it is not supported where CONFIG_ACPIGEN is not enabled.

The table shows the following information about each item:

Seq
    Sequence number in hex

Type
    Type of item

    =====  ============================================================
    Type   Meaning
    =====  ============================================================
    dsdt   Fragment of a DSDT table, as generated by a device
    ssdt   Fragment of a SSDT table, as generated by a device
    other  A whole table of a particular type, as generated by a writer
    =====  ============================================================

Base
    Base address of table in memory

Size
    Size of table in bytes

Device / Writer
    Name of device (for ssdt/dsdt) that wrote this fragment of the table, or
    name of the registered writer function (otherwise) that wrote the table.

acpi dump
~~~~~~~~~

Dump a particular ACPI table in binary format. This can be used to read the
table if you have the specification handy.

The name is the table's four-character signature and is not case-sensitive, so
`acpi dump spcr` and `acpi dump SPCR` show the same table. The address shown is
the one held in the list of tables, which on sandbox is not the address that
*acpi list* shows.

acpi set
~~~~~~~~

Show the address of the ACPI tables, or set it.

U-Boot knows where the tables are when it generates them itself. Where an
earlier firmware stage set them up, this command points the others at them, so
that the tables can be listed and dumped. The `ms` command can find them, since
the RSDP starts with the signature 'RSD PTR '.

With no argument the current address is shown instead.


Example
-------

    CSRT           66f9280     24  v00 U-BOOT U-BOOTBL 20261201 UBOO 7eac
    FACP           66f92b0    114  v06 U-BOOT U-BOOTBL 20261201 UBOO 1
    FACS           66f9240     40
    APIC           66f93d0     2c  v04 U-BOOT U-BOOTBL 20261201 UBOO 7eac

    SPMI           66f9450     41  v05 U-BOOT U-BOOTBL 20261201 UBOO 7eac

    00000000: 53 50 43 52 50 00 00 00 02 79 55 2d 42 4f 4f 54  SPCRP....yU-BOOT
    00000010: 55 2d 42 4f 4f 54 42 4c 01 12 26 20 55 42 4f 4f  U-BOOTBL..& UBOO

This shows the address of the tables, searches memory for the RSDP signature
and points the command at what it finds, which is how to reach tables that
U-Boot did not generate itself::

    => acpi set
    ACPI pointer: 66f9000
    => ms.s 66f8000 10000 "RSD PTR"
    066f9000: 52 53 44 20 50 54 52 20 d4 55 2d 42 4f 4f 54 02  RSD PTR .U-BOOT.
    1 match
    => acpi set 66f9000
    Setting ACPI pointer to 66f9000

Return value
------------

The return value $? is 0 (true) on success and 1 (false) on failure.

The dump sub-command fails if the name is not four characters long, or no table
of that name is present. The items sub-command fails where CONFIG_ACPIGEN is
not enabled. The list and set sub-commands always succeed; list says that no
tables are present rather than failing.
